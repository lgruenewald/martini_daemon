# Daemon architecture

Elements
- DaemonSystem
- DaemonTopology
- T* (TopStar)
- D/M algorithm

## DaemonSystem

List of particles, bonds, angles, ...

Main task: abstract away access to openmm internals. Only use the openmm API
from this file, never from any other class. In theory this means that it's
easier to port MartiniDaemon to either different engines than openmm, or to
replace which parts of the API are used. Optimizations such as buffering changes
and reinitializing only sparingly as needed should also be added here.

Later should be optimized to not duplicate in-memory information about
non reactive particles.

## DaemonTopology

A list of fragment types and reaction templates.

Fragment types can be:
- molecule fragment types (equivalent to a moltype from .itp's)
- incomplete fragment types (defined from .frag), which are always defined
  as a subset of particles of another fragment. These can be used to abstract
  parts of the molecule as capable of reaction, allowing different molecule
  types to react the same way. (TODO: find a different name, that's less
  confusing)

Molecule fragment types can be *instantiated*, which adds the particles and
their interactions to DaemonSystem and the corresponding fragment to T*.
Incomplete fragments get instantiated recursively when their corresponding 
"parent" fragment is instantiated (in their case instantiation only adds the
fragment to T*). Molecule fragment types can also be instantiated with
existing particles during the D/M algorithm.

Reaction templates contain the following information:
- reactant fragment types
- product fragment type 

## T*

List of fragments. A fragment is a grouping of particles and all the forces
that connect the particles.

Also contains a "defrag list", which is a list of fragments that each particle
is part of (as pairs of fragment id and the id of the particle inside the frag).

Should have helpers to generate a list of initiator atoms for D/M.

A fragment represents a molecule or a functional group for example.

Fragments can have three origins:
  - instantiated from a molecule fragment type
  - instantiated (recursively) from an incomplete fragment type
  - dynamically generated by the D/M (complete fragments)

Fragments have to obey the following rules:
- fragments can contain normal atoms and edge atoms
- a complete fragment is a fragment that contains no edge atoms
- an incomplete fragment is a fragment that contains edge atoms (not to be
  confused with incomplete fragment types, which map to .frag)
- all particles have to be a part of at least one complete fragment,
  which has to be the first element in their defrag list
- All particles that interact (bond, angle...) with normal atoms should be
  present in the fragment as at least edge atoms
- All fragments should contain an exhaustive list of all forces between its
  particles
  - all bonds and constraints containing a normal atom
  - all angles centered at normal atoms
  - all dihedrals that contain a normal atom as one of the "middle atoms"

These rules are guaranteed to be followed by:
- at the start of the simulation T* should be built to follow these rules
- the D/M algorithm should modify T* to keep T* compliant with these rules
Since it starts compliant and is only modified in a way to keep it compliant,
it should always stay compliant.

## D/M algorithm

T* should generate a list of initiator atoms and the fragment type.

DaemonTopology should generate a 2D matrix of fragment types, with the cutoff
distance contained in the cells for a quick access to whether two types can
react.

Updating the T* should be done following these rules:
- all forces in the reacting fragments should be removed
- the instantiated product fragment's particles should be 1-1 mapped to the
  two reactant fragment particles, with the same order
  - use incomplete fragment types to "reorder" if needed
- all fragments that contain atoms inside the reacting fragments (excluding
  edge atoms) will be removed from T*
- when the product fragment type represents a complete fragment, 
  it can probably be optimized to only instantiate this fragment
- otherwise, a new complete fragment should be generated as a union of all 
  complete fragments participating in the reaction (for A + B -> C)
- when instantiating the product fragment type, recursively instantiate all
  incomplete fragment types to handle reactive products
- dynamic fragments generated during the D/M algorithm can written to generate
  new .itp's for products generated during the reaction
